## 1. 目标、范围与原则

本计划用于验证仓库管理系统在明确的冻结版本上是否满足需求文档中的采购入库、出库成本核算、盘点、调拨、库存查询、预警、统计和登录访问控制要求，并验证页面、后端过程调用和数据库最终状态是否一致。

本轮分为两类工作：

1. **阶段一已执行**：版本与构建检查、应用启动、无登录访问拦截、页面路由与表单字段走查、基线阻塞定位；
2. **阶段二待执行**：正常/异常业务、FIFO/LIFO 成本、角色权限、数据库一致性、缺陷复测与最终演示。

本计划不包含以下内容：

- 不修改 Controller、Service、Mapper、存储过程或数据库结构；
- 不对未获 C 确认的数据库执行初始化、清空或回归 SQL；
- 不读取、记录或提交真实 `.env` 内容；
- 不在 B 未提供冻结 Commit、接口/异常说明及自测结果前给出最终质量结论；
- 不将“页面返回 HTTP 200”单独作为功能通过依据。

## 4. 测试策略与证据规则

### 4.1 执行顺序

1. C 确认隔离实验库、数据库服务、脚本版本和可重置窗口；
2. B 提供待测分支、冻结 Commit、接口/异常说明、变更清单和自测结果；
3. D 记录版本，运行 `mvn test`，启动应用，执行 BASE-001～BASE-010；
4. 先执行登录/权限、入库、出库，再执行盘点、调拨、查询、预警和报表；
5. 每一笔会写库的测试均在 C 允许的隔离数据组中执行；
6. 业务操作完成后由 C 的 `db/07-数据一致性验证.sql` 做只读核对；
7. 对失败项创建缺陷，收到修复 Commit 后先复跑原用例，再执行相关回归。

### 4.2 证据标准

每个“通过”结论至少包含以下任意组合：页面/HTTP 结果、后端返回或日志摘要、数据库查询结果。涉及写库的用例必须同时有页面结果与数据库结果；涉及事务的失败用例还必须有失败前后对比。

证据保存在 `docs/D/evidence/stage1/` 或后续 `docs/D/evidence/stage2/`。文件名使用“用例编号-场景-结果”格式，例如 `OUT-FIFO-001-result.png`、`DATA-CHECK-001-zero-rows.txt`。证据不得包含数据库密码、Cookie、会话标识或真实 `.env` 内容。

### 4.3 数据准备约束

1. 只能使用 C 确认的 `warehouse_c_lab` 隔离实验库或等价隔离库；
2. C 的文档明确初始化/回归会清空同名业务表，执行前必须由 C 确认当前可重置；
3. FIFO/LIFO 标准数据为：同一货品在同一仓先入库 `100 × 5.00`，再入库 `50 × 6.00`，随后出库 `120`；
4. FIFO 预期成本为 `620.00`、余量为 `30 × 6.00`；LIFO 预期成本为 `650.00`、余量为 `30 × 5.00`；
5. 调拨、盘点和库存不足场景必须在操作前记录库存、批次余额和单据数，失败后逐项比对；
6. 测试账号使用 README/C 交接中指定的演示账号，密码不写入本文件或证据。
